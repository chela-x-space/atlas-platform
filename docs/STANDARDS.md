# ATLAS Standards

These standards govern product and architecture work. Detailed behavior remains defined by implemented contracts and the versioned public API specification.

## Evidence First

Every canonical claim originates from an identifiable provider and retains sufficient provenance to verify it. Missing evidence remains missing; ATLAS does not manufacture substitute facts.

## Deterministic Before Intelligent

Identity, normalization, deduplication, ordering, priority, risk, and relationships use published, testable rules. AI may assist interpretation only after deterministic evidence boundaries exist.

## Canonical Data

Canonical intelligence has stable ownership and identity. Timeline, Search, Map, Risk, Reports, Entity Intelligence, Dashboard, and API are projections or presentations; they do not create competing truth.

## Source Attribution

Provider identity, source links, timestamps, freshness, and required attribution follow intelligence through every permitted projection and export.

## Provider Governance

A provider must have an approved identity, authority, scope, rights, collection policy, failure policy, and operational owner before activation. Availability is never inferred from configuration alone.

## Explicit Failure

Partial, stale, degraded, unavailable, and empty states are distinct. Previously verified stale data may be used only when clearly identified; upstream failure must not appear as a successful empty result.

## Marketplace Separation

Marketplace is a digital-product domain, not an intelligence source. Products, assets, licensing, and future commerce remain isolated from the Dashboard and canonical intelligence.

## AI Policy

AI outputs are non-canonical, evidence-grounded, cited, rights-aware, and reviewable. AI must not invent facts, silently alter ranking or risk, create unsupported relationships, or bypass authorization.

## Trust Before Scale

Provider quantity is not a success measure. Source authority, legal use, evidence quality, geographic coverage, freshness, and operational reliability take precedence.

## Architecture Before Implementation

New trust, identity, storage, delivery, commerce, or public API boundaries require explicit architectural approval before implementation. Planning milestones do not grant authorization.

## Compatibility

Existing canonical identities, routes, public API contracts, deterministic behavior, and attribution remain stable unless a human-authorized migration defines versioning, compatibility, validation, and rollback.
